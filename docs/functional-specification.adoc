Test environments
-----------------
At minimum, run the tests pre-release.  UI automation needs more work;
the most viable way is through accessibility APIs.
Also see link:configuring-your-system.adoc[about configuring a system].

 - Wayland: headless Weston
    * Use for automated tests.
    * No server-side decorations: check client-side decorations.
      Window shadows are expected to be rendered.

 - Wayland: GNOME's Hell (Mutter)
    * A major Linux desktop environment.
    * No server-side decorations: check client-side decorations.
      Window shadows are expected to be rendered.
    * Check if colour management works.
    * CSD: must invoke the right cursor on mouse move.
    * CSD: right clicks must invoke the compositor's context menu.
    * CSD: double click to maximise/restore must return
      to the original window positioning.

 - Wayland: Sway (wlroots)
    * Check if colour management works.
    * Have thumbnailing run in one window, send a new _dn_ window to another
      workspace, go to that workspace: _dn_ must not stall.

 - X11: i3 + picom
    * Check if colour management works.
    * Keep the window inactive, go to another workspace, go back:
      the window stays mapped the whole time, _dn_ must render on the expose.

 - macOS
    * Check if colour management works.
    * Watch idle CPU usage: we've had a situation with too frequent presents.

 - Windows
    * A major operating system.
    * Check if colour management works.

 - Linux + Wine

Setting `QT_SCALE_FACTOR` to 0.5 or 1.5 should not cause any issues.

Weston
~~~~~~
The `gl` renderer has been observed to render upside-down while `headless`.
This can be fixed with `--transform` but it hints at unreliability.

The `desktop` shell is useful for CSD testing, and the `kiosk` shell is useful
for not having to manage the window position.

```
unset DISPLAY QT_QPA_PLATFORM
weston --backend=headless \
  --renderer=vulkan --width=1600 --height=1200 \
  --socket=wayland-dn \
  --idle-time=0 \
  --debug
WAYLAND_DISPLAY=wayland-dn ./bin/dn
WAYLAND_DISPLAY=wayland-dn weston-screenshooter
WAYLAND_DISPLAY=wayland-dn weston-debug scene-graph
```

Other Weston backends seem to be useful for interactive testing.

Compositing
-----------
The UI is composited in linear light, with the exception of thumbnails,
which are both scaled and composited in encoded values.

Images with any transparency are conventionally composited in encoded values,
and scaling them in linear light would not match that composition.
Therefore, the viewer processes transparent pages in encoded values by default,
and thumbnail production scales transparent images in encoded values.
Both scale fully opaque images in linear light.

The HDR rendition of an image is shown when it has a gain map, the display can
show it, and the toggle is on.  It is always processed in linear light,
transparent or not, as nothing above SDR white has a convention for
compositing in encoded values.  This holds even while the display's current
headroom leaves no gain at all, so that a change in brightness never changes
how transparency composites.

Thumbnails
----------
When loading a directory, retrieve thumbnails as fast as possible:

 - First, rescale already loaded thumbnails from a different nominal size.
 - Then try to fetch existing thumbnails, in this order:
    * _wide-thumbnail-spec_
    * XDG _thumbnail-spec_
 - The nominal size is attempted first, then larger sizes, then smaller ones.

The wide thumbnail view is only happy with _wide-thumbnail-spec_ images
of the nominal size, with a declared gamut.

The square thumbnail view is also happy with nominal size _wide-thumbnail-spec_
images rescaled to fit the square.

If happiness is not achieved, create a new thumbnail, and try to save it.

While creating a thumbnail, fetching the thumbnail size itself before data helps
stabilise layout.  As of writing, there is no mechanism to pass this.
